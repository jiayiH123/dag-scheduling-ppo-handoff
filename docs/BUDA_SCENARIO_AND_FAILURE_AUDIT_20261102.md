# BUDA目标场景、当前适配差异与原因证据

2026-11-02。重读[作者IWQoS2022全文](https://xujia-njupt.github.io/xujia.github.io/Paper/2022IWQoS.pdf)§III/IV/V，核对当前`daglab/external_baseline_sim.py`，读取完整既有成绩，另做12例货币单位工程检查和1582条全量输入资格边界检查。没有替换或调参BUDA，没有新增模型训练/推理。

## 目标场景差异

|方面|论文BUDA|我们当前场景|
|---|---|---|
|目标/约束|最小makespan，预算与deadline同时满足|最小makespan，硬预算与累计资源容量，无deadline|
|处理资源|处理器可用时刻与串行排程模型；随机实验32/64处理器|3/4/6设备池，一个池在容量允许时并行多个任务，需求1–4|
|异构|任务相关速度SP(i,p)，同设备对不同类型任务的相对性能可以变化|任务工作量/池速度；一个池的速度系数对所有任务相同，另有容量约束|
|价格|每任务/设备按相对速度归一化，Price∈(0,1]；EC=ET×Price|每池固定整数费率，EC=duration_ticks×cost_rate，未保留原价格生成器|
|通信|平均网络带宽/时延，跨处理器边时延与同处理器0通信|实际源池/目的池带宽矩阵，固定可重叠通信时延|
|图规模|随机20–100任务，分子动力学41/表观基因组100等|原合成20/40/80/120，当前WF可至271，新增TRAIN至280|

当前BUDA保留HTCM排序和HTCT=EFT+HTCM选池，日历替换为累计资源插入，并加入后缀最低费用硬mask。它不是未经修改的原作者程序。原文Algorithm1虽输入deadline D，未出现按D逐任务过滤分支；不能声称“去掉deadline导致性能退化”。

## 已证实：货币尺度改变了时间—费用权重

原文归一化使EC≤ET；当前EC/ET等于整数池费率，可能大于1很多。HTCM直接加ET+EC，没有相应归一化时，排序及选池中的费用项权重会变化。这是源码和模型定义可直接确认的差异，但它对全数据集差距的贡献不能由公式单独确定。

已有历史全1862配置的解释控制（逐配置C/HEFT）：

|版本|合成862|旧WF200|旧TPC800|
|---|---:|---:|---:|
|主BUDA适配|2.384493|1.291572|1.060139|
|本地unitbalanced解释|1.109334|0.938791|0.892057|

该控制把费用项系数设为平均时间/平均费用；它改变了排序和选池，显著影响结果。这不是原论文作者版本，也不能按每题取二者最优作为BUDA。

本次工程检查将每条输入所有费率和总预算共同乘1000。每个映射的预算可行性保持等价，运行时长/资源/网络不变。12例里9例BUDA顺序或映射改变，5例实际工期改变；BHEFT的顺序、映射、工期12例均不变，费用仅按比例缩放。例：合成`val_simv1_val_00499_b1`，120任务6池，BUDA工期15700→22875，只改变了货币计量单位。该反例直接证明当前适配缺乏货币尺度稳定性，不能据此估计全体质量收益或断言它解释全部失败。

证据：`runs/teacher64_bheft_v2_20261102/BUDA_CURRENCY_ENGINEERING.json`，脚本`audit_buda_currency_units_20261102.py`。

## 已确认的实现解释与未闭合验证

1. 论文式12右侧仍写HTCM(Ti,Pj)，与左边自引用。当前解释为后继HTCM(Tk,Pj)递推；这需要原文表II/III/IV示例一致性验证，不能自称逐字复现。此次核对文本及PDF页面确认该打印形式。
2. 论文RAB初始化为最低费用总和，式16却减当前平均费用。当前主适配减当前最低费用来保持后缀账本，另存printedledger解释。这是明确的实现差异；历史主/printedledger成绩相同，暂不支持它是当时差距的主要来源。
3. 当前HTCM对不可执行的任务—池表项保留默认0，父节点同池前瞻可能误用该值。此边界对一般资格约束存在风险；但此次对当前全部862合成+400WF+320编程输入检查，所有任务均可单独放入所有池，风险触发数为0。因此它不能解释本轮这1582条的差成绩。累计容量争抢仍然存在，资格全可用不等于无限资源。
4. 从单处理器串行模型迁移到累计容量池后，固定HTCM对并行/排队的预测可能失配；任务相关异构变为统一池速度也会改变适用性。这些是待受控验证的机制假设，没有全量因果分解证据。

全量资格证据`BUDA_FULL_INPUT_ELIGIBILITY.json`；12例初查另存`BUDA_ELIGIBILITY_ENGINEERING.json`（12例同样未触发）。

## 当前判断和后续顺序

现有数据只能说明本地BUDA适配表现较差。证据最强、应最先核查的是价格/时间尺度与原文示例一致性，随后是打印歧义和累计资源模型适配。设备资格边界已被当前全量输入排除为本轮原因；缺少deadline也没有主因证据。不能将上述差异全都当成已证实的失败原因。

正式用作论文强baseline前，应先对齐原文示例，再冻结一个对本项目有明确单位和资源含义的版本，在相同完整面板重评；必要的正确性修复应与性能调参区分。本次只执行审计，不改既有baseline成绩。Teacher-v2标签生成与该工作独立进行。
